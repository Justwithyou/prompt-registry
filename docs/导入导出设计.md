# 个人提示词管理平台 导入导出设计方案

> 状态：已评审定稿，待落地  
> 日期：2026-10-08  
> 关联能力：数据备份 / 迁移（区别于「CLI/Skills 输出能力」与「WebDAV 同步」）

## 1. 背景与目标

用户在「设置 → 数据管理」中需要一种**可移植的数据备份 / 迁移**能力：把一个用户（设备/账号）上的数据完整导出为单个文件，再导入到另一个用户（设备/账号）上，做到跨用户、跨设备的交付与接管。

目标：

- 导出为单个、可交换的 JSON 文件，内容自描述、可校验。
- 导入到已有数据的库时支持两种模式（追加合并 / 覆盖清空）。
- 全程保留原始 ID 与层级 / 关联关系，做到「导出 → 导入」可近乎无损往返。
- 单事务保证要么全部成功、要么全部回滚，不产生半截数据。

## 2. 与既有能力的边界

| 能力 | 定位 | 是否复用本方案 |
| --- | --- | --- |
| CLI/Skills 输出（`crates/export`） | 把提示词渲染成 SKILL.md / md / json 供外部使用 | ❌ 不涉及（丢失 ID 与层级，无法还原结构化数据） |
| WebDAV 同步（`crates/sync`） | 同一用户多设备、同账号间的加密增量同步 | ❌ 不涉及（面向同一身份，非跨用户交接） |
| 存储位置迁移（`storage_location`） | 同机更换 `.db` 所在目录 | ❌ 不涉及 |
| **本方案：数据导入导出** | 跨用户 / 跨设备的全量数据交接 | ✅ 新增 |

## 4. 导出文件格式

单个 UTF-8 JSON 文件，建议文件名 `prompt-manager-备份-<时间戳>.json`。顶层结构：

```json
{
  "schemaVersion": 1,
  "platform": "prompt-manager",
  "exportedAt": "2026-10-08T12:00:00.000Z",
  "data": {
    "categories": [],
    "tags": [],
    "projects": [],
    "prompts": [],
    "promptProjects": [{ "promptId": "...", "projectId": "..." }],
    "promptTags": [{ "promptId": "...", "tagId": "..." }],
    "versions": []
  }
}
```

约定：

- `schemaVersion`：当前固定为 `1`，用于后续格式演进的前向/后向兼容判断。
- `platform`：固定 `prompt-manager`，导入时校验来源一致性。
- 实体字段沿用 `crates/core/src/models` 的 camelCase 序列化契约（与 IPC 一致）。
- **保留原始 ID**，使 `parent_id` / `category_id` / 关联表引用无需重映射即可还原层级关系。

## 5. 导入策略

### 5.1 导入模式

| 模式 | 行为 |
| --- | --- |
| 追加合并（默认） | 保留目标库现有数据，本方案数据按「跳过已有」并入 |
| 覆盖清空 | 先清空目标库业务数据（保留结构、`_migrations`、`sync_*`），再整体导入 |

### 5.2 ID 冲突策略

**跳过已有**：插入一律使用 `INSERT OR IGNORE`，遇到目标库已存在的同 ID 实体直接跳过，不覆盖、不破坏本地修改；关联表以复合主键去重。

### 5.3 事务与顺序

导入在单个 SQLite 事务内完成，按外键依赖顺序插入：

```
分类 → 标签 → 项目 → 提示词 → 提示词-项目关联 → 提示词-标签关联 → 历史版本
```

- 任一步骤失败即整体回滚。
- 「覆盖清空」模式下清空顺序与插入顺序相反，保证不触发残留引用。
- 新插入的提示词同步写入 `prompts_fts` 全文索引。

### 5.4 校验

导入前执行三类校验，任一失败即拒绝：

1. 文件可读、JSON 可解析。
2. `platform == "prompt-manager"`。
3. `schemaVersion` 受支持（当前 `== 1`）。

## 6. 架构落点

遵循既有分层（core 定义模型 / storage 负责数据访问 / ipc 负责命令 / 前端负责 UI），新增与改动如下：

| 层 | 位置 | 改动 |
| --- | --- | --- |
| 存储层 | `crates/storage/src/transfer.rs`（新增） | 定义 `DataBundle` 等类型 + `export_bundle` / `import_bundle` / JSON 与校验；直接基于 `Db` 做全表批量读写，统一事务 |
| 存储层 | `crates/storage/src/lib.rs` | 导出 `pub mod transfer` |
| 存储层 | `crates/storage/Cargo.toml` | 增加 `serde`（derive）依赖 |
| 命令层 | `src-tauri/src/data_transfer.rs`（新增） | `export_data` / `import_data` 两条命令，走 `ensure_unlocked` 网关 + `State<Db>` |
| 装配层 | `src-tauri/src/lib.rs` | `mod data_transfer` + 注册命令 |
| 前端契约 | `src/shared/api/commands.ts` | 新增类型与 `exportData` / `importData` |
| 前端 UI | `src/features/settings/ui/SettingsPage.tsx` | 「数据」分区新增导入/导出入口与报告展示 |

### 6.1 新增类型（Rust，`storage::transfer`）

- `DataBundle { schema_version, platform, exported_at, data: BundleData }`
- `BundleData { categories, tags, projects, prompts, prompt_projects, prompt_tags, versions }`
- `PromptProjectLink { prompt_id, project_id }` / `PromptTagLink { prompt_id, tag_id }`
- `ImportReport { categories, tags, projects, prompts, versions }`，每项为 `Count { imported, skipped }`

### 6.2 命令契约（前端 invoke）

| 命令 | 入参 | 出参 |
| --- | --- | --- |
| `export_data` | `{ path: string }` | `string`（写出的文件路径） |
| `import_data` | `{ path: string, overwrite: boolean }` | `ImportReport` |

## 7. 决策记录

已与用户评审确认：

1. **导入模式**：追加合并 + 覆盖清空都提供（`overwrite` 布尔切换）。
2. **ID 冲突策略**：跳过已有（`INSERT OR IGNORE`）。
3. **历史版本**：纳入导出/导入。
4. **入口位置**：设置 → 数据管理。
