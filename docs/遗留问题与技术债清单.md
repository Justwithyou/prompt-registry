# 遗留问题与技术债清单

**记录日期**：2026-09-30
**基线**：`main` @ `ff3f4b0`（`git tag m4-tag`）
**用途**：M1～M4 收口时未完全闭环、或在收口后发现的遗留项，集中留痕以便后续按编号逐条修复与回溯。每条含「现状 / 根因 / 影响 / 建议修复方向」。

## 遗留 #1 · M4 同步功能未装配（`sync_engine = None`）　✅ 已修复（2026-09-30）

- **修复状态**：已完成「完整闭环」修复。`sync_engine` 现以 `Arc<dyn SyncEngine>` 编入 `AppState`（`ipc::state`）；`configure_sync` / `sync_now` / `get_sync_status` 三命令已真实接线；`sync_key` 由 Master Key 经 HKDF（`crypto::derive_sync_key`）派生；`sync_log` 采集、落地回写（apply）、`SyncConfig` 持久化均已实现。验证：`cargo check` / `cargo test --workspace --exclude prompt-manager` / `cargo clippy --workspace --all-targets` / `cargo fmt --check` 全绿。
- **修复内容摘要**：
  1. `core`：新增 `SyncLogStore` / `SyncConfigStore` trait（从 sync crate 移入 core，避免 storage→sync 依赖倒置）。
  2. `storage`：新增 `migrations/0004_sync_log.sql`（`sync_log` / `sync_config` / `sync_meta` 表）+ `SqliteSyncLogStore`（`record`/`pending`/`apply`/`mark_synced` + 五类实体落地分发 + device_id 持久化）。
  3. `crypto`：新增 `derive_sync_key`（HKDF-SHA256，`SYNC_KEY_INFO = b"prompt-manager/sync-key/v1"`）。
  4. `sync`：`Engine` 改用 `prompt_core::SyncLogStore`；`sync_key` 改为 `RwLock<Option<[u8; 32]>>`，新增 `set_sync_key`（解锁后动态注入）。
  5. `ipc`：三命令真接线；新增 `sync_hook.rs` 为 CRUD 命令挂采集钩子；`state.rs` 装配 `sync_log_store`/`sync_config_store`/`sync_engine`；`vault.rs` 上锁时 `set_sync_key(None)`。
  6. `src-tauri/src/lib.rs`：新增 `assemble_sync`（构造 `SqliteSyncLogStore` + `AesGcmCipher` + `Engine` 并取 device_id），清理 `sync_engine = None`。
- **历史根因（修复前）**：M4 只实现了同步「零件」，装配链缺失（无 sync_log 表 / 无 SyncLogStore 生产实现 / 无采集钩子 / 无 apply 分发 / 无 sync_key 派生 / 无 SyncConfig 持久化）。
- **残余次要缺口**：见下方 遗留 #5。

## 遗留 #5 · M4 同步次要缺口（#1 修复后残余）

- **现状**：#1「完整闭环」修复后，单实体主链路（CRUD→采集→加密上传→下载解密→LWW 合并→落地→清日志）已通；但以下采集/覆盖范围仍未接：
  1. `batch_update` 批量更新命令未挂 `record_json` 采集钩子（批量写不产生 sync_log）。
  2. prompt 与 project/tag 的**多对多关系**（`set_relations` / `prompt_projects` / `prompt_tags`）未纳入同步载荷，跨设备归属关系不对齐。
  3. version 历史记录（M3 版本归档 / 回滚）未接入采集，历史版本不随同步传播。
- **根因**：M4 主链路聚焦单实体增删改，关联关系与批量/派生实体的采集属收尾边界未覆盖。
- **影响**：单设备内正常；多设备下批量操作、标签/项目归属、版本历史可能不同步或丢失。
- **建议修复方向**：为 `batch_update` 与 `set_relations` 补采集钩子；将关系表纳入 `apply_one` 分发与载荷；为 version 归档挂采集钩子。工作量小，可作为 M4 后续增量或并入 M5。

## 遗留 #2 · M4 数据库加密「落库」未装配

- **现状**：`src-tauri/src/lib.rs` 仍用 `Db::open(&db_path)` **明文**打开库；`vault` 为 `CryptoVault::new()`，其 `setup` 生成的包装信封（`Envelope`）只存内存、Master Key 只存内存，重启即失。`Db::rekey` / `Db::open_with_key` 仅被 `sqlcipher_test.rs` 调用，装配层未接。
- **根因**：M4 的 `rekey` 迁移与 `open_with_key` 就绪，但装配层未做「首次 setup 时 `db.rekey(key)`」「启动时按是否有口令决定 `open_with_key`」「信封持久化到库/配置」三件事。
- **影响**：M4 标称的「数据库加密、无口令无法读库」在真实应用里**未生效**——库始终明文，`unlock` 仅校验内存态，重启后 `vault` 状态清空。
- **建议修复方向**：见遗留 #1 同源（M4 装配收尾）；需设计「信封持久化位置 + 启动解锁时序」，连同 #1 一并立项。

## 遗留 #3 · M4 OS 钥匙串自动解锁未接线

- **现状**：`crypto::KeychainStore` / `CryptoVault::with_secret_store` / `auto_unlock` 均已实现并有单测，但 `lib.rs` 用 `CryptoVault::new()`（`secret_store = None`），`auto_unlock` 与前端「自动解锁」开关未接通真实 keyring。
- **根因**：M4 后端实现完成、装配层未接线（与 #1/#2 同类）。
- **影响**：「启用自动解锁」UI 形同虚设，重启后仍需手工输口令。
- **建议修复方向**：装配层 `CryptoVault::with_secret_store(Box::new(KeychainStore::new(...)))`，启动时调 `auto_unlock`，并与信封持久化（#2）统一时序。

## 遗留 #4 · `core` crate 命名与标准库冲突（pre-existing，非 M4 引入）

- **现状**：`Cargo.toml` 已注明「crate 名 `core` 与 Rust 标准库 core 冲突，引用处使用别名 `prompt_core`」。但 `cargo test --workspace`（含 doctest）中，`crates/core/src/errors.rs` 的 `#[derive(thiserror::Error)]` 在 rustdoc 单文件编译下展开出 `core::fmt`，被解析到自身 crate，报 `cannot find fmt/write in core`，doctest 失败。
- **根因**：crate 名 `core` 遮蔽标准库 `core` 命名空间；单元测试/集成测试编译路径未触发，仅 doctest（`rustdoc --test` 单独编译）触发。
- **影响**：`cargo test --workspace` 非零退出（表现为 doc-test 失败），可能阻塞 CI 的全量测试门禁。
- **建议修复方向**：将 crate 重命名为 `prompt-core`（`[package] name = "prompt-core"` + 移除别名 + 全仓引用统一），或为 `errors.rs` 显式导入以规避宏展开歧义；前者更彻底但改动面大，需独立处理。
